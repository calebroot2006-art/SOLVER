# Program plan

The director's plan for the whole product, written 2026-09-05 from `PRODUCT.md` and the
nine notes in `docs/research/`. Each phase below becomes its own `PLAN.md` (from
`templates/plan.md`) when it starts. This file says what gets built, in what order, who
builds it, and what proves it works.

## Principles that order the work

1. **Solver before game, game before coach.** The coach grades against the solver and
   the bots play from it. A wrong solver makes both worse than nothing.
2. **Enumerate cards before bucketing.** Heads-up postflop enumerates cards inside the
   specified betting tree and measures exploitability in that game. Bucketed preflop
   comes after, with separate abstraction diagnostics. Sampled spots do not certify
   unrestricted full-game exploitability (`solver-algorithms.md` section 8).
3. **Every grade carries its provenance.** A solve is an approximate equilibrium of a
   specified game: its bet menu, ranges, root history, payoff model, units, residual,
   and stop reason are stored with it and shown with any grade built from it.
   Exploitability is measured within that tree; it is not unrestricted no-limit
   exploitability, and a root residual is not a per-decision error bar. A decision the
   solver cannot cover (wrong ranges, off-tree history, 3+ players postflop) is marked
   approximate or ungraded, never invented.
4. **The coach's poker claims come from validated facts.** Grading and facts are
   computed in Rust. The language model selects and orders approved facts and
   templates; every substantive sentence the user reads is rendered from trusted data.
   Matching numbers alone is not a correctness check (an explanation can cite the right
   EV and still call an equal-EV mixed action mandatory). A validated template fallback
   always exists and has its own applicability tests.
5. **Own the data.** Charts the app ships are charts we solved. Anything Caleb pastes in
   for personal use is loaded from his files, never bundled.
6. **Fun is a requirement, not polish.** Caleb's chosen direction (recorded in
   `../ASTRA.md`) is a polished poker room with a friendly coach: the table is the main
   experience, the coach lives beside it, and play and study connect in both directions.
   Astra owns the design and reviews implementation against it. Bounded components
   may be delegated in isolated worktrees.
7. **Hand in hand with Astra.** Caleb's condition on the stack approval. In practice:
   every phase's `PLAN.md` goes to Astra through `docs/reviews/` before an executor
   starts; UI phases wait for Astra's designs; every phase ends with a review handoff and
   Astra's independent check of the numbers, the game transitions, the grading, and the
   security surface. Claude's own review is the first gate, not the last.
8. **Built to ship.** The audience is Caleb first and the public second. Shipped solves
   run on a 16 GB machine; heavy preflop solving happens once on bigger hardware and the
   results ship as data. Stack depth, table size, and tournament format are settings
   from the first line of code, never constants.

## Architecture

```
gto-solver-app/
├── crates/
│   ├── cards/        cards, decks, combos, 7-card evaluation, range parsing (Pio string)
│   ├── tree/         bet-size DSL, action tree, all-in threshold, pseudo-harmonic translation
│   ├── postflop/     DCFR solver, public-state tree, terminal sweep, isomorphism, compression
│   ├── bestresponse/ exploitability on the public-state tree, reported as % of pot
│   ├── payoff/       terminal payoff trait: chip EV, ICM, bounty-adjusted ICM
│   ├── preflop/      multiway MCCFR with bucketed postflop; produces range charts
│   ├── engine/       hand engine: 2 to 9 seats, blinds, antes, BB ante, straddles, side pots,
│   │                 blind schedules, single-table tournament, hand-history export
│   ├── bots/         policy from spot library + translation + bounded live re-solve; profiles
│   ├── spots/        solved-spot and range-chart file formats, library index, generator CLI
│   ├── coach/        grading (EV loss tiers, RNG mode), explanation input builder, templated
│   │                 explanations, language-model client with schema check, leak tracker
│   └── wasm/         wasm-bindgen wrapper (kept building, not shipped first)
├── app/              Tauri 2 + React + TypeScript
│   ├── src/table/    PixiJS table, GSAP motion, seats, cards, chips, coach corner
│   ├── src/study/    range grid, tree builder, solution browser, chart viewer, reports
│   ├── src/trainer/  drills, play mode, session review, leak dashboard, spaced repetition
│   ├── src/coach/    coach panel, "why?" view, settings (timing, voice, avatar on/off)
│   └── src-tauri/    commands, progress events, SQLite via tauri-plugin-sql
├── spots/            generated library (gitignored when large; regenerated by spots CLI)
├── docs/             PRODUCT.md, ROADMAP.md, research/
└── tests/            Kuhn and Leduc known values; PokerKit hand fixtures; reference solves
```

The contract between solver and app is the solved-spot format in `crates/spots`. The UI
never reaches into solver internals. Every crate has a README and its own tests.

## Phases

Each phase ends with something that runs, a test gate, and an updated README. "Who"
follows the CLAUDE.md rule: numerical solver code is built in the main session or by
`executor` with `model: "fable"`; UI, tooling, engine, and docs go to `executor` on
Opus; every build is reviewed in the main session before Caleb hears "done".

### Phase 0. Bootstrap

* **Build:** `git init`, Rust workspace with the crate skeletons, pnpm workspace for the
  app, `cargo fmt`/`clippy`, `prettier`/`eslint`, a GitHub Actions workflow that runs
  tests on Windows and Linux, `.gitignore` for `spots/`, `.env`, and build output,
  READMEs that say what each folder is for.
* **Gate:** `cargo test` and `pnpm test` pass on an empty project in CI.
* **Who:** `executor` (Opus). Blocked on Caleb confirming the stack (decision 1).

### Phase 1. CFR on Kuhn and Leduc

* **Build:** in `postflop`, a game trait and vanilla CFR, CFR+, and DCFR(1.5, 0, 2) with
  alternating updates and in-place rescaling; a best-response calculator for these toy
  games; Kuhn and Leduc implementations in `tests/`.
* **Gate:** Kuhn game value matches the known equilibrium (player 1 loses one eighteenth
  per hand) to 1e-4; Leduc matches OpenSpiel or noambrown/poker_solver; exploitability
  falls monotonically for DCFR on both.
* **Who:** main session (Fable). Research input: `solver-algorithms.md` sections 1 to 3.

### Phase 2. Cards, ranges, evaluation, terminal sweep

* **Build:** `cards` crate: card and combo types, Pio range-string parser and printer,
  13x13 mapping, card removal, 7-card evaluator (evaluate `deuce` and rs-poker on our
  benchmark, or write our own perfect-hash table), the Johanson three-bucket showdown
  sweep with inclusion-exclusion blockers, and a brute-force O(n²) reference.
* **Gate:** evaluator property-tested against brute force over 10 million random 7-card
  hands; sweep matches brute force on random ranges and boards including chops; range
  strings round-trip.
* **Who:** `executor` with `model: "fable"` for the sweep and evaluator; Opus for the
  parser. Research: `solver-algorithms.md` sections 4 and 5, `open-source-libraries.md`.

### Phase 3. River solver

* **Build:** `tree` crate (bet-size DSL in b-inary's vocabulary, raise cap, all-in
  threshold); `postflop` river solve over two ranges on one board; `bestresponse` on the
  public-state tree; exploitability as percent of pot; progress logging with timestamps;
  loud failure on NaN or out-of-memory.
* **Gate:** exploitability under 0.5 percent of pot on a standard river test set at 20,
  100, and 200bb; strategy frequencies within 2 percentage points of wasm-postflop on
  identical inputs, with every larger difference explained in the README.
* **Who:** main session. This is the highest-judgment code in the repo.

### Phase 4. Turn, river, then flop

* **Build:** chance nodes; suit isomorphism (use or port kdub0's hand-isomorphism index);
  parallel traversal over runouts with rayon; f32 storage first, then 16-bit compression
  with a measured error bound; `memory_usage()` estimate before allocation; the solve
  refuses to start if the estimate exceeds the configured limit.
* **Gate:** a 100bb single-raised-pot flop tree with two bet sizes solves to under 0.5
  percent of pot with measured peak memory (working buffers and desktop overhead
  included) recorded for a named set of trees and within the 16 GB target; f32 and
  compressed solves are each measured against the f64 baseline on the same inputs and
  their error recorded; flop frequencies cross-checked against wasm-postflop on the
  49-flop subset; all-in and pending-call fixtures pass (a bet that puts one player
  all-in still leaves the call-or-fold decision); suit merging is skipped when either
  range breaks the symmetry.
* **Who:** main session, with `executor` (fable) for isomorphism and compression once the
  f32 version is validated.

### Phase 5. Solved-spot format and library generator

* **Build:** `spots` crate: the file format (header with format, positions, stack depth,
  tree config, exploitability, solver version; per-node strategy and EV per combo;
  compact binary plus JSON export), the range-chart format (Pio string plus JSON
  wrapper), a CLI that solves a flop subset (25, 49, 85, 184) for a given preflop
  scenario and writes the library, and an index SQLite table.
* **Gate:** round-trip tests; a 25-flop library for one scenario generated end to end
  with a log Caleb can read.
* **Who:** `executor` (Opus). Blocked on decision 2 (formats first) only for which
  scenarios to generate, not for the format itself.

### Phase 6. Game engine

* **Build:** `engine` crate: seats 2 to 9, dealer button and blinds, antes and big-blind
  ante, straddles, dead blinds, betting rounds, all-in with multiple side pots, showdown
  and chop, hand history export, blind schedules, single-table tournament with
  eliminations and payouts. `payoff` crate with the chip-EV implementation and the ICM
  trait stub.
* **Gate:** replay of PokerKit's published hand fixtures (including the 2023 WSOP final
  table hands) produces identical pot distributions; property tests that chips are
  conserved in every hand; rs-poker's arena used as a second oracle.
* **Who:** `executor` (Opus), reviewed by main session. Independent of phases 3 to 5, so
  it runs in parallel with them in its own worktree.

### Phase 7. App shell and study tools

* **Build:** Tauri 2 shell; React with TypeScript; PixiJS table with GSAP motion for
  deals, bets, and pot movement, readable at 6, 8, and 9 seats; game setup (format,
  table size, stack depth 10 to 200bb); range grid editor; tree builder; solution
  browser (frequencies, EV, equity, filters, per-street navigation); solve screen with
  live progress; SQLite storage. The chart viewer is built but stays dark until phase 11
  produces our own ranges.
* **Gate:** a spot built in the UI solves through the Rust core with progress shown and
  is browsable; a chart file loads and renders; the table deals a full hand from the
  engine at 60 fps on Caleb's machine.
* **Who:** Astra designs and implements the screens and owns all of `app/**` including
  `app/src-tauri`. Claude's side delivers the crate APIs (solve, progress stream,
  solved-spot loader, engine) with typed contracts specified in writing before either
  side builds; Astra wires them into Tauri commands, or hands Claude a bounded,
  file-specific task to do so. Independent of phase 6 except for the shared engine API,
  so it can start once phase 5's format is fixed.

### Phase 8. Bots and play mode

* **Build:** `bots` crate: preflop policy from range charts (placeholder ranges we
  generate ourselves, clearly labelled, until phase 11 produces solved ones), postflop
  policy from the spot library with pseudo-harmonic
  translation of the user's off-menu sizes, a bounded live re-solve (river, then turn)
  when the spot is missing, mixed-strategy sampling, timing variance, and a hook for
  style profiles. Play mode in the app: cash ring game at 6, 8, or 9 seats.
* **Coverage table (required before this phase starts, Astra R06):** for every play and
  grade path, the supported game, the range and history inputs it needs, the
  approximation used, the bot's fallback policy, and whether a solver grade is allowed.
  The first version of that table, to be completed in this phase's PLAN.md:

  | Situation | Bot policy | Grade |
  |---|---|---|
  | Preflop, any seat count | Range chart for the exact position and action sequence | Chart-based, labelled by chart source |
  | Postflop heads-up, in library, on-menu sizes | Library strategy | Solver grade with residual |
  | Postflop heads-up, off-menu size | Pseudo-harmonic translation, then library | Approximate, translation shown |
  | Postflop heads-up, not in library | Bounded live re-solve (river, then turn) | Solver grade with that solve's residual, or ungraded on timeout |
  | Postflop 3+ players | Labelled legal fallback policy (no solver claim) | Ungraded until a validated multiway model exists |

* **Gate:** bots complete 10,000 hands against each other without engine errors; per
  situation in the coverage table, a logged sample of decisions shows the bot used the
  stated policy with matching ranges and history; aggregate frequencies match the
  library within sampling error where a library policy applied; 3+ player postflop
  decisions are recorded as fallback and produce no solver grade; a full 6-max session
  is playable end to end.
* **Who:** `executor` (Opus) for the policy plumbing; main session for the live re-solve
  path.

### Phase 9. Coach v1

* **Build:** `coach` crate: grading on EV loss into Caleb's four tiers (correct, good,
  medium, bad) with RNG mode so a correct mixed-strategy action is never penalised, each
  grade carrying the source solve's provenance and an "uncertain" state when the
  evidence cannot resolve a difference; the fact builder (stable fact IDs for action
  frequencies, EVs, equity, blockers, board texture, pot odds, built only from
  information available at the decision); the validated template library with
  applicability tests; the Claude client (Sonnet 5, cached system prompt, structured
  output per the current API, returns approved fact and template IDs, credentials in
  Rust only, bounded size, time, retries, concurrency, and cost, cache keys tied to
  decision, solve revision, prompt revision, and model, stale results discarded); leak
  tracker per spot category and street; spaced repetition queue of missed spots. In the
  app (Astra's): a "why?" button on the hand just played, shown after the hand ends; the
  end-of-session review that lists hands by tier and lets Caleb pick which to see
  explained; leak dashboard; drill mode built from the queue. Text only. The coach
  never speaks unasked and has no during-hand control.
* **Gate:** tier assignment matches a hand-built test set including equal-EV mixes;
  every explanation in a 200-hand test session is rendered from validated facts and
  passes the adversarial fixtures (equal-EV mixes, swapped actions, percent versus
  fraction and bb versus chip confusion, stale or mismatched solves, unsupported
  multiway spots, fabricated blockers, future-card leakage, prompt text embedded in hand
  data); rejected, refused, truncated, and offline responses all fall back to an
  applicable template; cancellation, stale results, and rate limits are tested; the
  network-off path works; no coach output appears while a hand is in progress.
* **Who:** the assigned executor builds the `coach` crate. Astra owns the app views
  and Tauri integration, and may delegate file-specific components against the written
  contract. All changes pass Astra's review.

### Phase 10. Tournaments

* **Build:** `payoff` ICM implementation (Rust port of the poker-apprentice
  Malmuth-Harville with Monte Carlo fallback), configurable payout tables (1 to N paid),
  satellite payoffs (N equal tickets), knockout and progressive-bounty payoffs with
  bounty power, bubble factor and risk premium calculators the coach can cite, ICM
  terminal payoffs in the solver, push-fold trees, tournament play mode (sit-and-go,
  single-table MTT stage, satellite) with blind schedules and big-blind ante, and
  tournament grading against the right payoff model.
* **Field model (Astra R06):** a satellite with 25 tickets or an MTT pay jump cannot be
  represented by one nine-seat table. This phase adds a simulated off-table field
  (stacks, eliminations, payout and bounty state advanced between hands) so ICM and
  ticket payoffs have a real field behind them, while Caleb plays one table. Full
  multi-table play with balancing stays in Phase 13; this phase's tournament modes are
  labelled "table stage with simulated field" in the app.
* **Gate:** ICM equity matches poker-apprentice's test vectors; push-fold ranges match
  published Nash charts heads-up; satellite and bounty payoffs pass hand-built cases; a
  9-player sit-and-go, a bounty sit-and-go, and a 25-ticket satellite with a simulated
  field are each playable to completion with correct payouts; tournament grades use the
  tournament payoff model, never chip EV, and say so.
* **Who:** main session for the payoff substitution; `executor` (Opus) for the rest.

### Phase 11. Multiway preflop solver and our own charts

* **Build:** `preflop` crate: postflop bucketing (equity histograms, k-means with earth
  mover's distance, using robopoker's `elkan` and `monge` if they hold up), external
  sampling MCCFR over the multiway preflop tree with bucketed rollouts, and a chart
  generator for 6, 8, and 9-max at chosen depths. Then the bunching correction in the
  postflop solver. Then a 3-way postflop river solver as a stretch goal.
* **Gate:** wasm-postflop does not solve preflop, so first capture (a) an independent
  small-game reference: OpenSpiel `universal_poker` with an ACPC definition
  of a heads-up preflop-only game (push-fold, then a limited-raise tree) solved with
  its CFR, matched by our solver on identical inputs with the reference residual
  recorded; and (b) published heads-up Nash push-fold charts with matching assumptions.
  The ACPC game, terminal payoffs, and reference execution must be verified before
  this becomes a runnable acceptance gate. Then compare 6-max RFI ranges within a few
  percent of free HRC and GTO
  Wizard sample spots, with differences explained. Sampled full-game exploitability
  checks are labelled diagnostics, not certificates, and exist to catch abstraction
  overfitting.
* **Who:** main session. The hardest research problem in the repo; gets its own
  `researcher` pass on bucketing before it starts.

### Phase 12. Launch readiness

* **Build:** interactive click-through charts lit up from phase 11's ranges (required
  before launch); the coach's API path for a public build (a small proxy service holding
  the key, or a user-supplied key; Caleb decides); installer, updater, and Windows code
  signing; onboarding; crash and error reporting that never sends hand data without
  consent; a licence audit of every dependency; Astra's security assessment of file
  imports, solve resource limits, permissions, and the network path.
* **Gate:** a clean Windows machine installs and runs the app; the licence audit shows
  only MIT, Apache, or equivalent; Astra's security review has no open demonstrated
  defect.
  The release scope must also be explicit: a simulated tournament stage does not
  fulfill the complete MTT requirement below. Caleb must decide any reduced launch
  scope before release; this roadmap does not assume that decision.
* **Who:** `executor` (Opus); Astra for design and security.

### Phase 13. Depth

Face and voice for the coach (Rive avatar, browser speech, then ElevenLabs), pre-action
warnings as an optional setting, hand-history import, exploit profiles for bots (tilted
solver frequencies), multi-table tournaments with balancing, WASM browser build, mobile.
Each is planned when its turn comes.

The complete tournament requirement remains part of the product. Phase 10 delivers
single-table sit-and-gos and labeled stages with a simulated field. Phase 13 must
demonstrate complete freezeout MTT, knockout, progressive-bounty, and satellite
events: all field stacks, eliminations, payout and bounty state, seat moves, table
balancing, final-table transitions, and final awards. Test 6-, 8-, and 9-seat tables
where the event rules allow them. Record format-specific payout and chip-conservation
fixtures before implementation. A completed stage is not evidence that this gate passed.

## Decisions

All seven original questions were answered on 2026-09-05 and are recorded in
`docs/research/README.md` and `PRODUCT.md`. Two remain for the launch phase: the
coach's API path in a public build (proxy service versus user-supplied key) and Windows
code signing.

## What happens now

1. `planner` writes `PLAN.md` for phase 0 and phase 1 together (small, one worktree).
   The plan goes to Astra through `docs/reviews/` and to Caleb before execution.
2. `executor` bootstraps the repo (phase 0). Main session reviews, merges, then builds
   phase 1 in the main session.
3. From phase 2 on, one `PLAN.md` per phase, executors in worktrees, main session
   reviews every diff and runs the accuracy gates itself, then Astra reviews.
